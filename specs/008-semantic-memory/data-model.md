# Data Model: Semantic Memory

## Memory

Represents a fact retained for semantic use in a user's future chats.

| Field | Type | Rules |
|---|---|---|
| `id` | string | Required, unique opaque identifier generated by the application |
| `user_id` | string | Required, non-empty after trimming; all store operations are scoped to this owner |
| `fact` | string | Required, non-empty after trimming |
| `embedding` | BLOB | Required normalized vector for `fact`; exactly 384 little-endian Float32 elements (1,536 bytes), finite values |
| `created_at` | date/time | Required creation timestamp |

### Relationships and persistence

- A user is identified by `user_id`; this feature does not add a users table or define authentication.
- A user may own zero or more memories. A memory belongs to exactly one user.
- Persist records in the SQLite `memories` table with exactly the fields above. Add an index on `user_id` to scope exhaustive recall and deduplication to the owner.
- Encode vectors as 384 little-endian binary 32-bit floating-point values. The model ID/revision and encoder configuration must remain consistent for all records in this table; changing model/vector dimensions requires a future migration or re-embedding strategy.
- Bind all user-controlled values and fact strings as prepared-statement parameters. Never construct SQL from them.

## MemoryStore operations

| Operation | Input | Result and rules |
|---|---|---|
| `remember` | `userId`, `fact` | Embed the fact; compare only that user's records; if one or more dot products are strictly greater than `0.92`, do not insert a duplicate and return the existing memory with the highest score; otherwise persist and return a new memory. The duplicate check and conditional insert are atomic. |
| `recall` | `userId`, query text | Embed the query; rank only that user's records by descending dot product; take at most three candidates, then retain only records with score strictly greater than `0.3`. |
| `forget` | `userId`, memory ID | Delete only the matching record owned by that user; report whether a record was deleted without revealing another user's record. |

### Validation and lifecycle

- Validate `userId` and fact/query strings as non-empty after trimming before model or store access.
- Encoder output must have the expected dimensionality and only finite values; reject invalid outputs rather than persisting them.
- Stored BLOB length must be exactly 1,536 bytes before decoding; reject corrupt, non-finite, or wrong-dimensional vectors rather than returning plausible results.
- The encoder emits normalized vectors, so dot product is cosine similarity. Apply strict deduplication `> 0.92`; for recall, sort descending, slice the first `k` candidates, then keep only scores `> 0.3`.
- When scores tie, use a stable deterministic secondary ordering so repeated recalls have a predictable result.
- A successful forget removes the record from subsequent recall. An ID that is missing or belongs to another user results in no deletion.
- Embedding or storage errors are failures and must propagate; an empty recall is valid only when there are no matching memories above the score threshold.

## Chat request context

The chat service uses required `userId` to request recall before invoking the existing reasoning strategy. The retrieved facts are composed as explicit memory context alongside the current user message. Memory records themselves are not returned to the chat caller by this feature; the existing answer and metrics contract remains in effect.
